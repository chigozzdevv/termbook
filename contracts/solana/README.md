# Solana SOL collateral

The program holds native SOL in a per-lock PDA and seized SOL in a per-credit recovery PDA. The SOL owner signs `Lock`. Monad Core must first bind the lock and publish its exact lock digest through Wormhole. The Solana wallet adapter posts that VAA to Wormhole Core on Solana; `Lock` verifies the posted VAA before taking custody.

For release, seizure, expiry, recovery funding, and recovery payout, Monad Core publishes the exact action hash. The program accepts only a Wormhole Core `PostedVAA` from the pinned Monad Core emitter with that hash. It checks the lock binding, amount, recipient, nonce, revision, and deadline before changing balances. Each transition emits the updated lock or recovery record through the Wormhole Solana emission shim. Monad verifies the signed snapshot VAA before recording the transition. `CheckpointLock` emits a fresh lock snapshot when the original VAA has aged out; resubmit its transaction signature to the lock tracking endpoint. `CheckpointRecovery` emits a fresh recovery snapshot after a pending action expires so Monad can prove non-execution. `ReconcileRecoveryRefund` records only SOL actually returned to the recovery PDA.

The program pins the Wormhole Solana Core and emission shim mainnet program IDs. It requires a posted Monad VAA and eleven shim accounts after the instruction's normal accounts. `Lock` also requires the executing program account and its ProgramData account and rejects an active upgrade authority. The shim accounts, in order, are payer, bridge, message, emitter, sequence, fee collector, clock, system program, Wormhole Core, event authority, and emission shim. The SDK browser wallet posts the Monad VAA and prepares these accounts; other wallet implementations can use the same port. The server fetches the signed VAA by finalized Solana transaction signature from WormholeScan and ABI-encodes the account key and proof selectors for `SolanaVerifier`.

Wormhole Guardians are part of the security model. A signed VAA attests to the source program's message; it does not independently prove the program binary. Before market admission, remove the program's upgrade authority and run `node --import tsx server/scripts/verify-solana-program.ts <rpc-url> <program-id> <genesis-hex> <program-data-hash>`. Use its hex program and emitter values to deploy `WormholeSolanaAccountClient`, then admit the resulting `SolanaVerifier` and configure Monad Core's Wormhole address through governance. The configured Wormhole Core and shim must match the target networks. The SDK uses an injected Solana wallet with `connect` and `signTransaction`; it posts Monad VAAs using Wormhole's Solana Core SDK. Set `SOLANA_PROOF_URL` to the WormholeScan API origin and supply the finalized Solana `sourceTx` signature to confirmation endpoints. A live lock, release, seizure, and Aurora recovery cycle remains a deployment validation gate.

Run `cargo test --offline` here. `cargo build-sbf --offline` builds `target/deploy/sol_collateral.so`; preserve the ignored `target/deploy/sol_collateral-keypair.json` to retain the program ID. The local SBF smoke script checks invalid bindings against a loaded program. It does not simulate Wormhole Guardians or prove a live cross-chain cycle.
